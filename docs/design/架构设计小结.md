# PureSource + BT-Player 架构设计小结

> 日期：2026-05-09
> 基于 BT-Player 现有 VPS 部署（Oracle 首尔 ARM, bt.mgtv.dev）的演进方案

---

## 一、当前状态与定位修正

BT-Player 已在 VPS 上运行，具备基本的磁链解析、文件树识别、HTTP Range / local-stream 和本地文件交付能力，当前以 VPS 现网状态为事实源。

经过浏览器播放端多轮测试，以及对 GitHub 现有磁链播放方案的横向检索，当前项目定位已经从"自研磁链播放器"修正为：

> **磁链资源提纯 + 播放路由器。**

这个修正很重要。播放器端，尤其是浏览器 `<video>`、自研 Web 播放管线、边下边播 seek、远程 MP4 缓冲策略和容器兼容，是一个投入巨大且收益不稳定的坑。当前项目不再把"自己完成稳定播放"作为主目标，而是把复杂资源整理成成熟播放器可以消费的 URL、本地文件、缓存资产或播放任务。

因此：

- BT-Player Web 端主要承担输入、预览、状态展示、文件选择和路由入口。
- 稳定观看优先交给 PotPlayer / VLC / mpv / 系统播放器等成熟执行层。
- PureSource / BT-Player 的核心价值在于 magnet metadata、peer 状态、文件树、正片识别、缓存成熟度、faststart/remux、质量评分和播放路由。
- 早期关于 HLS 化、浏览器内播放、ffmpeg 中继、自研播放执行器的设想不删除，但降级为**可选研究线或特殊场景能力**，不再作为当前 MVP 的主承诺。

经过多轮讨论，我们围绕这个新定位设计了一套"资源线索 → 提纯 → 缓存 / 检测 → 播放路由"的组合式架构，并完成了一系列方案文档和案例推演。

### 2.1 核心锚点：PureSource 负责提纯，BT-Player 负责路由

BT-Player 不应被设计成一个吞下所有复杂来源的万能播放器。网络视频资源外层可能包裹着资源站页面、广告脚本、动态 JS、反盗链、短时效 Token、磁链合集、云盘入口或播放器壳，但最终一定会指向某种更纯净的媒体源：

- 一个可直接读取的 MP4 / MKV / TS 等媒体文件
- 一个 m3u8 清单及其分片组
- 一个磁链中的正片文件
- 一个云盘或 WebDAV 中的真实文件对象
- 一个已经缓存到 VPS 本地的可播放文件

**PureSource 的核心职责，就是剥离这些外壳，找到真正承载视频内容的干净播放对象。**

BT-Player 的职责则应收缩为：接收 PureSource 输出的标准化播放对象，并把它交给最合适的执行层。它不负责猜测资源站逻辑，不负责反盗链突破，不负责判断磁链中哪个文件是正片，也不负责把所有下载和播放策略都硬塞进同一个播放接口。对于稳定观看，它更应该生成 PotPlayer / VLC / mpv 可以消费的 URL、本地文件路径或播放任务，而不是继续承诺浏览器内稳定播放。

换句话说：

> **PureSource 负责把复杂来源提纯为干净、可验证、可路由的播放对象；BT-Player 负责缓存治理、状态呈现和播放路由；成熟播放器负责最终稳定播放。**

因此，PureSource 的输入不应被理解成单个 URL，而应被理解成一个**资源线索集合**。用户粘贴的可能是一条磁链、一个 m3u8、一个视频网页，也可能是一整段论坛文本，里面同时包含磁链、种子文件名、下载站 URL、截图、标题和说明。浏览器代理提交的也可能不是单个视频源，而是列表页中的一组候选视频、一次运行时捕获到的多个 m3u8、密钥请求和页面上下文。

PureSource 的输出也不应只是"一个链接"，而应是经过提纯、验证、评分和路由建议的**标准播放对象**：

- 这个资源真正的媒体主体是什么
- 哪些文件是正片，哪些是广告、样本、字幕或附加内容
- 当前来源是否可播放，是否需要 Referer、Cookie、密钥或浏览器代理
- 是否支持 Range，是否适合边下边播，是否需要先缓存
- 同一资源是否存在多个候选源，哪个源质量更高
- 推荐交给外部播放器、local-stream、qBittorrent、hls.js 预览，还是仅展示元数据
- 是否进入 PotPlayer 外部播放列表，以及进入哪个只读专辑

这一定义可以避免后续实现退回到"用户粘一个链接，BT-Player 直接试着播"的旧思路。BT-Player 面对的应该是 PureSource 已经整理好的播放对象，而不是未经提纯的复杂网络来源。

### 2.2 组合式播放系统，而不是单一万能方案

后续架构应明确采用组合式系统思路：不同模块只承担自己最擅长的职能，再通过数据契约协同起来。

- 浏览器代理负责运行时嗅探，处理服务端无法直接看到的真实 URL、m3u8、密钥和短时效参数。
- PureSource 负责源发现、磁链提纯、广告过滤、文件树识别、可播放性验证、质量评分和播放路线推荐。
- 下载 / 缓存引擎负责把不稳定来源变成本地可控资源，可包括 librqbit、qBittorrent、PikPak、WebDAV 或后续云缓存层。
- 播放执行层负责具体播放，当前主执行层应优先采用 PotPlayer / VLC / mpv / 系统播放器；BT-Player Web、hls.js、本地 Range 服务或 HLS 切片服务只作为预览、辅助或实验能力。
- 播放列表层负责把已提纯、已筛选的可用资源输出为 PotPlayer 可订阅的只读 `.m3u8` 专辑。
- 路由决策层负责判断当前资源应进入 PotPlayer 播放列表、直接交给外部播放器、先缓存、交给 qBittorrent 顺序下载、生成本地资产、进入 Web 预览，还是仅展示元数据。

PotPlayer 的启发在于：成熟播放器擅长播放 URL、本地文件和外部协议，但它并不会天然理解复杂资源站页面，也不会替系统完成磁链提纯、反盗链分析、广告过滤和资源质量判断。因此，BT-Player 的长期方向不是复制 PotPlayer，而是让 PureSource 先把复杂资源提纯成干净播放对象，再交给合适的播放执行层。

### 2.3 播放执行层应外部优先，Web 播放降级为预览

PureSource 负责判断"这是什么资源、质量如何、应该怎么处理"，但最终播放仍需要根据媒体形态选择不同执行方式。BT-Player 不应把播放方式固定为单一的 `<video>`、rqbit `/stream` 或本地 Range，而应在播放执行层保留多种策略：

- 如果提纯结果已经是成熟播放器可消费的 URL 或本地文件，则优先生成外部播放器任务。
- 如果是普通 MP4 / MKV / TS 等本地文件，BT-Player 可以提供本地 Range URL，但默认目标是给 PotPlayer / VLC / mpv 消费。
- 如果提纯结果本身就是可用 HLS，则可交给 hls.js 做 Web 预览，也可生成外部播放器可打开的 m3u8 URL。
- 如果容器或编码不适合浏览器直接播放，ffmpeg 可用于转封装或转码，但这不意味着要把 Web 播放作为主路线。
- 如果输入是正在增长的缓存文件，可以研究 ffmpeg 中继或 HLS 分片，但应明确为实验线。
- 如果目标是更强的网页播放兼容性，可以将文件转成 HLS 的 m3u8 + TS / fMP4 分片；该方向保留为后续研究，不进入当前 MVP 主承诺。
- 如果资源较大或来源不稳定，可以先进入缓存队列，达到可播阈值后再启动播放。

这里的重点不是预设唯一答案，而是让播放层根据标准播放对象选择最合适的执行器。当前的首选执行器应是成熟外部播放器；Web 播放、hls.js、ffmpeg relay、HLS 分片缓存都可以保留，但需要标清它们是预览、辅助或后续研究，而不是当前系统的稳定主播放承诺。

因此，BT-Player 的播放层应逐步从"一个接口返回一个 URL"演进为"播放路由与执行器调度器"：

```
标准播放对象
  ├── external_ready    → PotPlayer / VLC / mpv
  ├── local_file        → local-stream Range URL，优先给外部播放器消费
  ├── hls_direct        → 外部播放器 / hls.js 预览
  ├── browser_unsupported_container
  │                     → ffmpeg remux / transcode，产出外部播放器可消费资产
  ├── growing_file      → wait buffer / cache_first；ffmpeg relay 仅作实验
  ├── magnet_partial    → qBittorrent / rqbit 缓存调度后再播放
  └── metadata_only     → 展示文件树、peer、质量判断，不承诺播放
```

### 2.3.1 实测校正：Web `<video>` 不应作为主播放承诺

2026-05-11 对 `Cosmos Laundromat` 样本做过一轮 VPS 播放卡顿取证。该样本先后验证了以下事实：

- VPS 端服务、Caddy、HTTP Range 和静态文件分发均可用。
- `Cosmos_Laundromat.faststart.mp4` 已通过 faststart 重封装，`moov` 已前置。
- 文件编码为常见 Web 友好组合：H.264 High、`yuv420p`、AAC LC、约 2.4 Mbps。
- 使用浏览器直接打开 `https://bt.mgtv.dev/Cosmos_Laundromat.faststart.mp4`，即便取消 DevTools 网络限速，仍在 16-17 秒附近出现明显卡顿。
- 使用同一个 URL 导入 PotPlayer，仅短暂缓存后即可流畅播放，并且拖动进度条表现稳定。
- 直接把原始 magnet 链接交给 PotPlayer，无法播放，提示文件不存在或被锁定。

这组对照说明：当前链路已经能产出一个成熟播放器可稳定消费的媒体 URL，但浏览器原生 `<video>` 对远程 MP4 的缓冲、Range 调度、seek 策略和播放管线并不可靠。问题不再主要表现为"源不可用"或"服务端不可用"，而是 Web 播放执行器本身不应承担稳定主播放的承诺。

同时，这组对照也说明 PotPlayer 不能替代 BT-Player / PureSource 的前处理价值。PotPlayer 是播放执行器，不是资源提纯器；它擅长消费已经可读的媒体 URL 或本地文件，但不会替系统完成 magnet metadata 获取、peer 连接、文件树识别、正片选择、缓存成熟度判断、faststart/remux 或播放路由。

因此，后续路线应做以下校正：

- BT-Player Web 可以保留为轻量预览、状态展示、源选择和播放路由入口。
- 对稳定观看有要求的资源，应优先交给 PotPlayer / VLC / mpv / 系统播放器等成熟执行层。
- PureSource 的标准播放对象不仅要给出 `stream_url`，还应给出推荐执行器，例如 `web_preview`、`external_player`、`local_asset_playback`、`hls_player`。
- "可用源池"的判定应区分"浏览器可播"和"成熟播放器可播"。同一个 URL 在 PotPlayer 中流畅，不代表它适合作为 Web `<video>` 主播放源。
- "播放执行器可用"也不代表可以跳过源提纯层。原始 magnet 仍需要 BT-Player / PureSource 先转化为成熟播放器可消费的 URL 或文件。
- 不应继续围绕 Edge/Chrome `<video>` 的远程 MP4 卡顿做无边界调参；更高价值的方向是源提纯、容器/编码检测、播放路由和外部播放器交付。

一个更贴近实测的执行器建议可以写成：

```json
{
  "playback": {
    "webPreview": "available_but_not_primary",
    "recommendedExecutor": "external_player",
    "externalPlayerHint": "potplayer | vlc | mpv",
    "reason": "browser_remote_mp4_pipeline_unstable"
  }
}
```

### 2.3.2 PotPlayer 外部播放列表通道：当前最优闭环

基于 PotPlayer 专辑设置中的能力，可以把"外部播放列表（只读）"作为当前阶段最优先的播放通道。截图中 PotPlayer 已经提供了几类入口：

- 默认播放列表。
- 文件夹导航。
- FTP / WebDAV / HTTP 搜索。
- 外部播放列表（只读）。

这意味着 BT-Player / PureSource 不必尝试从网页直接唤起 PotPlayer，也不必先做本地 helper 或自定义协议。更自然的闭环是：VPS 生成 PotPlayer 可订阅的远程播放列表，PotPlayer 把它当作一个只读专辑来消费。

推荐闭环：

```text
magnet / URL / 网页线索
  → PureSource 提纯
  → 文件树与正片识别
  → 缓存成熟度 / 可用源池筛选
  → BT-Player 生成稳定 URL / 本地资产 / 外部播放器入口
  → VPS 输出 m3u8 播放列表
  → PotPlayer 外部播放列表（只读）订阅
  → 用户在 PotPlayer 专辑中直接选择播放
```

这个通道的优势是：

- 充分利用 PotPlayer 自带的专辑和播放列表能力。
- VPS 只输出标准播放列表，不承担播放器内核。
- 用户侧不需要浏览器唤起本地程序，也不需要额外安装 helper。
- 播放列表可以持续刷新，PotPlayer 侧保持一个固定入口。
- 资源是否进入列表由 VPS 控制，避免把不可播、未缓存、metadata 不完整的条目暴露给播放器。

因此，当前项目可进一步收敛为：

> **VPS 上的磁链资源提纯服务 + PotPlayer 可订阅播放列表后端。**

#### 生态分工与不过度提纯原则（2026-05-11 补充）

当前路线必须避免把 PureSource 做成新的 PikPak、qBittorrent、迅雷、解析站或播放器内核。PikPak、油猴脚本、资源站解析器、外部下载器、qBittorrent 等都已经在各自领域提供成熟能力；PureSource 的价值不是重造这些轮子，而是把它们的结果统一登记、归一化、标注状态，并路由给合适的播放执行层。

更准确的分工是：

```text
PureSource        = 资源馆 / 状态机 / 路由器 / 外部结果接收层
PikPak            = 云缓存、秒存、下载能力
油猴脚本 / 解析器 = 页面资源发现与直链提取能力
PotPlayer/VLC/mpv = 播放执行层
qBittorrent/rqbit = 可选探测或缓存能力，不默认进入主链路
```

因此，后续 magnet enrich 的第一步只应把磁链从"黑盒 pending"变成"可读 pending"：提取 `info_hash`、`dn`、`trackers` 等 URI 层信息。除非另行立项并明确接受风险，不应在 PureSource 主服务里默认接入 DHT、peer、libtorrent、qBittorrent 或 rqbit，也不应把拉 metadata、文件树、正片识别直接等同于播放出口。

同时，既然当前选择 PotPlayer 作为主播放端，PureSource 也不应追求把所有资源净化成统一、完美、浏览器可播的标准资产。PotPlayer 的优势正是网络 URL、播放列表、容器兼容、seek 与缓冲容错。PureSource 只需把资源整理到"PotPlayer 愿意接、用户看得懂、风险可控"的程度：

- 有明确 `stream_url` 且 PotPlayer 可打开，即可视为 `external_ready`。
- 不强制把 MP4、HLS、云盘直链、外部脚本结果统一转码或统一封装。
- 不为了浏览器 `<video>` 播放而过度清洗资源。
- 不为了"完美 metadata"阻塞已经可由成熟播放器消费的资源入列。
- 外部工具产生的直链、云缓存出口、人工提交的 URL，都是 PureSource 的合法上游输入。

一句话：**PureSource 不是播放器的前置净化厂，而是播放器生态的资源调度台。**

#### 播放列表格式建议

优先输出 UTF-8 的 `.m3u8`，而不是本地编码不确定的 `.m3u`。列表保持简单，先使用通用 M3U 扩展格式：

```m3u
#EXTM3U
#PLAYLIST:BT-Player 可用源池

#EXTINF:-1,Cosmos Laundromat | 1080p | stable | PotPlayer 推荐
https://bt.mgtv.dev/play/local/cosmos_laundromat_faststart.mp4?token=readonly_xxx

#EXTINF:-1,Some Movie | 720p | cached | subtitle: zh
https://bt.mgtv.dev/play/local/some_movie.mp4?token=readonly_xxx
```

字段原则：

- `#EXTM3U` 必须作为第一行。
- `#EXTINF` 的标题应面向人读，包含片名、清晰度、状态、推荐执行器等轻量信息。
- URL 使用绝对 HTTPS 地址。
- 文件名和 URL 尽量 ASCII / URL-encoded，避免播放器侧编码问题。
- `.m3u8` 全部使用 UTF-8，适配中文标题。
- 列表中只放 `stable` 或明确可由成熟播放器消费的资源；`metadata_ready`、`caching`、`failed` 等状态留在 Web 状态页，不进入主播放列表。

#### VPS 端接口建议

```text
GET /playlists/potplayer/default.m3u8
  默认可播放列表，只放 stable / playable 条目。

GET /playlists/potplayer/recent.m3u8
  最近提纯完成或最近缓存完成的资源。

GET /playlists/potplayer/movies.m3u8
  正片资源列表。

GET /playlists/potplayer/debug.m3u8
  仅调试使用，可包含 preview_ready 或实验条目，不配置到常用专辑。
```

每个播放 URL 不直接暴露内部路径，而是通过 BT-Player 的只读播放入口：

```text
https://bt.mgtv.dev/play/local/{asset_id}?token=readonly_xxx
https://bt.mgtv.dev/play/stream/{asset_id}?token=readonly_xxx
```

#### 鉴权与 Caddy 匹配原则

PotPlayer 消费远程播放列表时，不适合依赖复杂浏览器态、Cookie 注入或需要手动设置 Header 的方案。VPS 端应优先采用播放器友好的只读鉴权：

1. 播放列表 URL 使用长效只读 token。
2. 播放项 URL 使用同一只读 token 或短期签名 URL。
3. token 只允许访问播放列表和媒体读取接口，不允许调用管理、删除、解析、导入等 API。
4. Caddy 对 `/playlists/potplayer/*` 与 `/play/*` 采用单独的只读访问策略。
5. 如果后续验证 PotPlayer 对 Basic Auth 的体验稳定，可以作为第二选择；初期更推荐 URL token，降低配置摩擦。

#### 与 Web 状态页的分工

PotPlayer 专辑只看干净播放列表；BT-Player Web 页面负责复杂状态：

```text
PotPlayer 专辑
  stable / playable / external_ready
  只负责看和选。

BT-Player Web
  pending / metadata_ready / caching / low_peer / failed / metadata_only
  负责解释为什么暂时不进播放列表。
```

这样可以避免 PotPlayer 里堆满打不开的条目，也能保留 Web 端对资源提纯、缓存和诊断的解释能力。

### 2.3.3 上游出口实证（2026-05-11）：油猴 m3u8 与 PikPak VIP CDN

在确立「PureSource = 资源调度台」边界之后，必须用具体上游回答一个问题：**哪类外部工具的产出，是 PotPlayer 可以直接当 `stream_url` 消费的"裸 URL"？** 这个问题的答案，决定了 `default.m3u8` 里"一等公民出口"的范围，也决定了未来连接器要不要承担额外的 Header / 凭据复现工作。

2026-05-11 对两条候选路径做了实证，结论如下。

#### 一、油猴脚本 → m3u8（已实证）

样例：`https://cdn.hdcdn.online/.../index.m3u8`

由油猴脚本在浏览器运行时从资源站页面捕获到的 HLS 入口 URL。导入 PotPlayer 测试通过：可直接播放，无需在 PotPlayer 里额外设置 Header / Cookie。

**意义：**

- 油猴脚本是合法的上游"发现"通道：浏览器侧抓 URL → 提交 PureSource。
- 这类 URL 本身往往带短时效签名或 CDN 限频，但**裸 URL 形态成立**——可直接走 `POST /tasks` → `probe` → `promote` 闭环。
- 若 `probe` 因 CDN 严格策略偶发不准，仍可凭"PotPlayer 手验通过"经验直接 promote 入列；这是「PureSource 不追求过度净化」原则的具体体现。

#### 二、PikPak VIP「外部播放器」入口 → CDN 直链（本次新发现）

PikPak 客户端内置 PotPlayer 作为外部播放器；VIP 账户可在此入口截取到 PikPak 实际派发给播放器的 CDN URL。URL 形态（脱敏示意）：

```text
https://dl-z01a-0027.mypikpak.com/download/?fid=...&expire=1778579884&sign=...&userid=...&fileid=...
```

**curl 验证（关闭 PikPak 客户端，无 cookie / UA / Referer）：**

```text
HTTP/1.1 200 OK
Server: openresty/1.21.4.1
Content-Type: binary/octet-stream
Content-Length: 13339968
Accept-Ranges: bytes
Etag: "4ed79dd8c4bebba0f23676d86575cdc6"
Access-Control-Allow-Origin: *
X-Tos-Storage-Class: STANDARD
```

**关键响应头解读：**

| 响应头 | 含义 |
|--------|------|
| `200 OK`（无 cookie / UA / Referer 也成立） | **真·裸 URL**，与 PotPlayer 缓存 / PikPak 客户端注入 Header 均无关 |
| `Accept-Ranges: bytes` | 支持 Range，seek / 拖动进度条可正常工作 |
| `Access-Control-Allow-Origin: *` | CORS 全开；浏览器 JS 亦可直接 fetch，为将来 Web 端轻量 probe 留出空间 |
| `Content-Type: binary/octet-stream` | 非 `video/mp4`，但 PotPlayer 按 magic bytes 与扩展名识别，无害 |
| `X-Tos-*` | 底层为火山引擎 TOS 对象存储；PikPak 仅套签名 + 下载路由壳 |

**约束（必须心里有数）：**

| 约束 | 说明 | 对架构的影响 |
|------|------|--------------|
| 有效期约 24h | URL 中 `expire=` 为 Unix 秒；实测约 86400 秒寿命 | 列表里挂的 PikPak 条目几天后必然失效，需重新导入 |
| IP 绑定 | URL 在签发时绑定本机出口 IP | **本机签 → 本机播** 永远 OK；VPS / 公司网 / 4G 等不同出口 IP 会 403 |
| 仍需"选对文件" | PikPak 客户端里需人工挑选磁链中的正片 | 这正是「例 2 多文件磁链」的未解难题；PikPak 出口本身不解决文件树识别 |
| URL 含会话凭据 | `userid` / `sign` 等同于短期凭据 | 不应粘进公开文档 / 截图 / git；本机 JSON 持久化也要意识到这一点 |

**升格结论：** PikPak VIP CDN 与油猴 m3u8 同级，是 **一等公民出口**。例 1 的"单文件磁链"和例 2 的"多文件磁链"的播放出口问题，至少在 PikPak 通道上**已经打通**。

##### 补注：PikPak 运行机制实证（2026-05-11 二次 curl）

同日做了一次"1.3 GB 正片"量级的二次 curl 验证（不同 magnet、不同 download node：`dl-z01a-0054.mypikpak.com`）。除了再次证实"真·裸 URL"形态外，几个响应头同时揭示了 PikPak 后端的若干工作机制。这些机制对当前 PureSource 主线**不要求做任何改动**，但影响"未来若要做半自动连接器"的设计预期，归档备查。

**A. "秒存"实际上是全平台 info_hash 去重，不是同步秒成功**

对比两次的 `X-Tos-Create-Time`：

| 实证 | Content-Length | X-Tos-Create-Time |
|------|----------------|--------------------|
| 一次（小样本） | 12.7 MB | `Sat, 28 Sep 2024`（数月前） |
| 二次（1.3 GB 正片） | 1.3 GB | `Mon, 11 May 2026 01:39:15 GMT`（与本次转存几乎同时） |

可推断 PikPak 转存有两种路径：

- **真·秒存**：若该 info_hash 在 PikPak 全平台已被任意用户存过，新转存只是引用既有对象，几秒内出 CDN URL。
- **首次入库**：若该 info_hash 在全平台尚无对象，PikPak 后端代你下载 magnet → 上传到火山 TOS → 才出 CDN URL；视资源体积与做种活跃度，可能产生**分钟级到小时级**延迟。

**架构含义：** 任何针对 PikPak 通道的"自动化连接器"都**不能假设"调一次 API 就能拿到 URL"**——需要轮询任务状态、容忍冷门资源的入库等待。这是为什么这类连接器**不该住进 PureSource 主服务**，而应作为独立进程在外部承担。

同时这也意味着，**冷门 magnet 第一次塞进 PikPak 的用户会在 PikPak 数据库里留下 `userid → info_hash 首次入库` 的记录**——这是 PikPak 那一侧的事实，PureSource 管不了，使用者需自行评估。

**B. 大文件用 S3 multipart upload，对 PureSource 透明**

二次实证里 Etag 形如 `"8bcdf4a2…-2"`，且伴随 `X-Tos-Mp-Parts-Count: 2`——这是 S3 multipart 协议的标准标记。一次实证里 Etag 形如 `"4ed79dd8…"` 无尾缀，也无 `X-Tos-Mp-Parts-Count`，是直传小对象。

**架构含义：** PikPak 大文件 / 小文件在 CDN 层行为一致（HTTP Range 仍正常工作），**PureSource 无需区分**。仅作为"火山 TOS 真实存在"的旁证。

**C. download node 按文件/region/shard 分发**

两次 host 不同：`dl-z01a-0027` vs `dl-z01a-0054`。同一账户、同样 VIP 等级，host 在签名时由 PikPak 后端选定，URL 签名本身和 host 无强绑定关系。

**架构含义：** 若将来要在前端 / `probe` 里识别 "这是不是一条 PikPak URL"，**不能用单一 host whitelist**；应当用更宽的特征匹配，例如：

- host 后缀 `*.mypikpak.com/download/`
- query 同时含 `expire`、`sign`、`userid`、`fileid`

但这件事**今天不实现**，仅归档。

**D. CDN 后端坐实为火山引擎 TOS**

两次响应头都带 `X-Tos-*` 系列字段（`X-Tos-Request-Id`、`X-Tos-Storage-Class`、`X-Tos-Server-Time` 等），且 `Server: openresty/1.21.4.1`。可以判定 PikPak 把 ByteDance 火山引擎 TOS 当对象存储，前置 OpenResty 做签名验签与下载路由。

**架构含义：** 中性事实。火山 TOS 在境内出口稳定、Range 支持完整、CORS 全开；意味着 PikPak 通道的可靠性下限不低。但**不应基于此推断 PikPak 一定会持续提供这种"裸 URL 导出"能力**——这是 PikPak 客户端的实现细节，未来版本可能加入额外鉴权头、强制客户端启动等限制。**PureSource 不应把 PikPak 当成稳定 API 依赖**。

---

综上，**PikPak 的运行机制核心实证为：全平台 info_hash 去重 + 火山 TOS 后端 + 多节点签名分发 + 客户端导出"裸 URL"作为外部播放器入口**。这些机制对 PureSource v0.3 主线**零影响**；它们只影响"将来若要做 PikPak 半自动连接器"的设计预期，给出几条硬约束：不可同步、不可单 host 识别、不可依赖 PikPak API 稳定性、需接受 24h 寿命 + IP 绑定 + 凭据敏感等已知约束。

#### 三、对 PureSource 的实际意义

1. **`POST /intake` 端点是这类"外验通过"场景的正确入口** —— 绕过 `pending → probe → promote` 状态机，直接以 `external_ready` 入列。已有 v0.1 兼容路径足够，**无需新代码**。
2. **`probe` 不再是入列的必要条件**：在 PikPak / 油猴等"PotPlayer 手验已过、但 `probe` 可能 403"的场景下，`/intake` 是绕道；`/tasks → probe → promote` 是默认道。两条路并行存在，符合「调度台不强制唯一工作流」的产品形态。
3. **CORS 全开打开了一扇门**：未来若要在工作台前端做轻量可达性检测（如打开页面时自动 probe 列表里 PikPak / m3u8 条目是否仍存活），可以**在浏览器 JS 里直接 fetch**，无需绕回 8090 后端。今天不实现，但归档备查。
4. **连接器始终住在 PureSource 之外**：拿 URL 这一刀（油猴 POST 回 PureSource，或 PikPak 客户端导出后人工/脚本 curl `/intake`），**永远住在 PureSource 之外**；PureSource 主服务边界不动，沿用「资源调度台」的角色。
5. **磁链播放出口已实证一种路径**：例 1 / 例 2 的"magnet → 播放"难题，至少在「PikPak VIP 转存 + 导出 CDN URL + /intake 入列」这条通道上已经走通；其它通道（qBittorrent 本地缓存 + 自托管 Range、PikPak 之外的云盘服务）可后续比对，但**今天不必扩展**。

#### 四、待办备忘（不在本次实施）

以下几项随着"一等公民出口"实证出现需求，但**当前不做**，留作后续小节立项依据：

- `ResourceRecord` 是否需要 `expires_at` 字段 + 列表层过期跳过 + UI 倒计时（PikPak 24h 是常态）。
- UI 是否需要"已外验通过，直接入列"按钮（前端调 `/intake`，绕开 `/tasks` 流）。
- 是否需要"重新导入同一文件"的便捷流（PikPak URL 失效后最常见的操作）。
- `data/resources.json` 里 PikPak URL 含会话凭据这一事实，是否需要在 cutover 文档里加一行"PikPak 类条目不要 rsync 到 VPS"。
- 多文件磁链的"选正片"难题：仍未解；PikPak 通道把它推给了 PikPak 客户端的人眼操作，PureSource 不主动承担。

这些都不阻塞当前主线，亦不改变 PureSource 已稳定的 v0.3 状态。

### 2.4 播放时机：引入可播阈值和缓冲成熟度

实测中出现过一个重要现象：浏览器长时间暂停后，同一资源播放变得更流畅。这说明播放卡顿不一定意味着资源不可用，也不一定意味着播放器彻底失败；很多时候真正的问题是**边下边播阶段缓冲不足**。

因此，播放层不仅要决定"用哪个执行器播放"，还要判断"现在是否适合开始播放"。对于磁链、正在增长的缓存文件、弱网直链或需要中继的资源，BT-Player 不应在解析成功后立即硬播，而应引入可播阈值：

- 当前文件整体下载进度。
- 起播位置附近是否已有连续可读数据。
- 前 30 秒 / 60 秒媒体数据是否足够。
- 当前下载速度是否高于视频码率。
- 当前缓冲能支撑的预计播放时长。
- 用户拖动到目标位置时，该位置附近是否已经缓存。

当资源尚未达到可播阈值时，前端应给出明确状态，而不是让用户误以为"已经能播但很卡"：

```
正在预缓存...
已获取文件信息，正在准备连续播放区间。
预计缓冲达到 60 秒后开始播放。
```

这也解释了成熟播放器体验更稳定的原因：它们不仅拿到 URL，还会管理缓冲、预取和起播时机。对于 BT-Player 来说，"暂停后变流畅"应被视为一个设计信号：**缓存成熟度是播放体验的关键变量**。

后续标准播放对象应增加播放准备状态，例如：

```json
{
  "playability": {
    "state": "not_ready | buffering | playable | stable | metadata_only",
    "bufferedSecondsEstimate": 45,
    "downloadRateBytesPerSec": 2500000,
    "mediaBitrateBytesPerSec": 900000,
    "recommendedAction": "wait_buffer | play_now | cache_first"
  }
}
```

这样，PureSource / BT-Player 不再只回答"有没有链接"，而是回答"现在能不能流畅播放，以及应该等多久"。

### 2.4.1 源提纯后的可用源池

opencode 审查中提到的"连接池"在技术语境里主要指数据库连接池，但这个词对 BT-Player 更有启发意义的是产品层抽象：系统不应把所有输入链接都视为立即可播资源，而应建立一个经过提纯后的**可用源池**。

这里的可用源池不是数据库连接池，也不是简单 URL 列表，而是经过合法性、元数据、连接活性、下载速度、文件识别和播放适配性筛选后的播放候选集合。它回答的问题不是"有没有源"，而是"哪些源已经足够可靠，值得交给播放器"。

可分为三层：

```text
原始源池
  用户粘贴、浏览器代理捕获、网页文本解析得到的所有磁链、m3u8、直链、网页入口和云盘线索。

候选源池
  格式正确，能解析出基本信息，可能存在真实媒体主体，但尚未确认是否适合稳定播放。

可用源池
  已确认 metadata 可获取、连接活性足够、速度基本达标、正片文件明确、容器/编码或执行器路径可接受。
```

因此，播放卡顿不应被立即归因于"播放器失败"。很多卡顿本质上是源还没有通过可用源池筛选：peer 不足、下载速度低于码率、缓存区间不连续、目标文件识别不准，或者当前执行器并不适合该媒体形态。

推荐的判断链路是：

```text
原始链接
  → 格式/合法性检查
  → metadata 可用性
  → 连接活性与 peer 状态
  → 下载速度与码率对比
  → 正片文件识别
  → 播放执行器适配
  → 进入可用源池
  → play_now / wait_buffer / cache_first / external_player / reject
```

这个抽象能把 BT-Player 从"用户给一个链接，系统立刻硬播"升级为"先判断源是否值得播放、是否适合现在播放、是否应该缓存后再播放"。对当前 VPS 卡顿问题来说，优先要判断的是源质量和缓存成熟度，而不是直接扩大播放器功能。

### 2.5 BT 缓存优先、HLS 轻路由、外部播放器主执行

对于不同媒体来源，系统不应采用同一种播放策略。一个重要结论是：**HLS / 直链资源应轻量路由，BT / 磁链资源应优先缓存，再作为本地媒体资产交给成熟播放器播放。**

#### HLS / 直链：轻量路由，而不是重做播放器

如果 PureSource 提纯后得到的是可用 m3u8、mp4 直链，且所需 Referer、Header、Cookie、密钥等上下文已经明确，则应直接进入播放执行层：

```text
source_type = hls | direct_url
  → route_play
  → external_player / hls.js preview / 轻量反代
```

HLS 本身就是面向播放设计的流媒体形态，不需要再经过 qBittorrent 或 BT 缓存队列。对于可用的 m3u8，系统重点应放在多码率选择、Header 注入、AES-128 密钥处理、分片有效性验证和外部播放器交付上。`hls.js / <video>` 可保留为 Web 预览能力，但不再作为稳定观看的主承诺。

#### BT / 磁链：缓存优先

BT 的天然问题是 piece 不连续、做种波动、seek 位置不可预测。与其让浏览器直接面对这种不确定性，不如把 BT 资源交给更成熟的下载/缓存执行器，先将不稳定来源变成本地可控文件。

推荐策略：

```text
source_type = magnet | torrent
  → cache_first
  → qBittorrent executor
  → threshold policy
  → local asset playback
```

qBittorrent 的价值在于：

- 添加 magnet / torrent。
- 开启 sequential download。
- 开启 first / last pieces 优先。
- 按文件选择，只下载 PureSource 识别出的正片。
- 监控下载速度、进度、ETA。
- 达到预览阈值后允许试播。
- 完整缓存后登记为本地媒体资产。
- 交给 BT-Player local-stream 生成本地 URL，优先由 PotPlayer / VLC / mpv 打开；ffmpeg remux 或 HLS segment 作为后续加工能力。

这条路线不是放弃即时体验，而是更诚实地承认 BT 的不确定性：磁链解析成功并不等于资源适合立即播放。系统应通过缓存阈值把不稳定的 BT 供应转换成稳定的本地播放资产。

#### 缓存状态分级

BT 资源可采用分级状态，而不是简单的"能播/不能播"：

```text
metadata_ready
  已拿到文件树，可展示文件列表、大小、字幕、正片推荐。

preview_ready
  首部/尾部/前 N 秒可读，可尝试预览。

playable
  下载速度高于媒体码率，且缓冲达到 60-120 秒。

stable
  文件已完整缓存，可作为本地媒体资产，交给成熟播放器稳定播放。

archive_ready
  可转 HLS、入库、收藏、长期缓存或云导出。
```

因此，PureSource 的推荐结果中应包含播放策略，而不仅是播放 URL：

```json
{
  "recommended": {
    "strategy": "route_play | cache_first | wait_buffer | local_asset_playback | metadata_only",
    "executor": "external_player | local_stream | qbittorrent | hls_preview | ffmpeg_job",
    "reason": "BT source is unstable; cache first, play after stable threshold"
  }
}
```

这使系统形成清晰分工：PureSource 负责判断资源类型和推荐策略；qBittorrent 负责把 BT 资源缓存成稳定文件；BT-Player 负责生成状态、URL、本地资产和外部播放器任务；HLS/直链资源则绕过 BT 缓存队列，直接进入播放路由。

### 2.6 可直接借鉴和接入的成熟能力

PureSource 不应从零重写所有源发现、下载、解析和播放能力。当前文档和旧资产中已经有一批可以直接借鉴或轻量接入的成熟能力，应作为后续落地优先级。

#### ① 解析器.md → PureSource Browser Agent

`解析器.md` 已经是现成的浏览器侧运行时嗅探资产，不是纯概念。它具备：

- `fetch` hook：拦截运行时请求。
- `XMLHttpRequest` hook：捕获 XHR 加载的 m3u8。
- `<video>` 元素扫描：直接发现页面里的视频源。
- `m3u8-parser`：解析 manifest、多码率和分片信息。
- `GM_xmlhttpRequest`：绕过一部分 CORS 限制。
- Referer / Origin 辅助注入。
- CORS fetch → FileSystem API → GM 下载的三级降级。

因此，第一优先级不是重新写浏览器插件，而是把 `解析器.md` 改造成 **PureSource Browser Agent**：从"发现后本地下载"升级为"发现后提交给 PureSource，必要时继续承担浏览器代理执行职责"。

#### ② yt-dlp → 外部 fallback 提取器

`yt-dlp` 的最大价值不是下载本身，而是其成熟的站点提取器生态和标准化输出能力：

- 1800+ 站点 extractor。
- `--dump-json` 可输出结构化元数据。
- 通用提取器可作为未知站点兜底。
- 支持 cookies、headers、Referer 等上下文。
- 可借鉴其 extractor registry、Generic fallback、info_dict 输出契约。

PureSource 初期不需要深度嵌入 Python，建议先以系统工具方式轻集成：

```bash
yt-dlp --dump-json <url>
```

然后将输出转换为 PureSource 的标准播放对象。这样可以快速获得大量站点的提取能力，同时保持 Rust 主服务简单。

#### ③ you-get / lux → 提取器设计参考

`you-get` 对中文视频站支持经验丰富，适合参考中文站点的域名路由、DASH 音视频分离、通用嗅探策略。`lux` 的提取器接口极简，适合作为 Rust `SourceExtractor` trait 的设计参考。

这两者初期不一定作为运行依赖，但应作为 PureSource 内部提取器注册表、站点路由和故障隔离的设计样板。

#### ④ HLS 工具链 → 标准对象与预览能力

如果 PureSource 提纯结果已经是 HLS，则不应重复转码，而应直接生成标准对象、外部播放器入口或轻量代理：

- 前端播放：hls.js，仅作为预览或特殊场景能力。
- 服务端解析：Rust `hls_m3u8`。
- 高级下载/解密参考：N_m3u8DL-RE。
- 转封装、切片、中继：ffmpeg。

HLS 方向的重点是把 m3u8 资源标准化为可路由对象：多码率选择、Referer/Header 注入、AES-128 密钥处理、分片有效性验证、必要时转成本地 HLS 缓存。这里保留了 Web 播放可能性，但当前优先级低于外部播放器交付和资源质量判断。

#### ⑤ ffmpeg → 媒体加工执行器，不是 Web 播放万能补丁

ffmpeg 应作为 BT-Player / PureSource 的通用媒体加工执行器，而不是只用于单点修复，也不应被误解为"只要接入 ffmpeg 就能补平 Web 播放端所有问题"：

- MP4 faststart / moov 前置。
- 容器转封装，例如 MKV → MP4。
- 浏览器不兼容编码时转码。
- 生成 HLS 的 m3u8 + TS / fMP4 分片，作为后续研究线。
- 对正在增长的缓存文件做 relay 或分片中继实验，仅在明确有收益时推进。

ffmpeg 相关操作应默认异步化，进入任务队列，不阻塞提纯主流程。

#### ⑥ qBittorrent → BT 下载/缓存执行器实验

rqbit 适合轻量解析和当前最小主线，但从播放体验看，不宜无限承担高质量边下边播主线。qBittorrent 更适合验证：

- sequential download。
- first / last pieces 优先。
- Web API 状态查询。
- 慢资源进入缓存队列。
- 下载完成后交给 BT-Player local-stream 生成可消费 URL / 文件路径，并路由给外部播放器；ffmpeg/HLS 作为加工或预览备选。

qBittorrent 初期应作为执行器实验线，而不是立刻替换 rqbit。它的价值是验证"磁链提纯后，如何更稳定地把资源变成本地可播放文件"。

#### ⑦ GitHub 现有磁链播放方案 → 路线参照

2026-05-11 对 GitHub 上的磁链播放、BT 流媒体和外部播放器桥接方案做过一次横向检索。结论是：磁链播放器并不是空白领域，已有项目大多采用"BT 处理层 + HTTP/缓存/转封装层 + 成熟播放执行层"的组合路线，而不是单纯依赖浏览器 `<video>` 直接硬播。

可借鉴项目按类型分为五组：

| 类型 | 代表项目 | 可借鉴点 |
|------|----------|----------|

这些项目给 BT-Player / PureSource 的路线启发是：

- 不应从零重做完整磁链播放器生态。
- `rqbit` 可以继续作为 Rust 侧 BT 引擎和 HTTP API 基座，但不应独自承担全部播放体验。
- 外部播放器桥接是成熟路线，不是退让；PotPlayer/VLC/mpv 的价值在于承担稳定执行层。
- 自托管服务的关键不是"网页里能打开"，而是"能把磁链变成被不同终端稳定消费的资产"。
- Stremio/debrid 类项目说明，源聚合、质量评分、缓存命中、执行器选择，是比单点播放控件更长期的产品能力。

因此，本项目后续不宜继续自称"磁链播放器"并与 WebTorrent Desktop、Stremio、VLC/mpv 插件类项目正面竞争。更准确的定位是：

```text
BT-Player / PureSource = 资源提纯与播放路由器
  输入：magnet / torrent / m3u8 / 网页 / 混杂文本
  处理：metadata、peer、文件树、正片识别、缓存、faststart/remux、质量评分
  输出：成熟播放器可消费的 URL / 本地资产 / HLS / 外部执行器建议
```

#### 落地优先级

```
1. 解析器.md → PureSource Browser Agent
2. yt-dlp subprocess fallback → 快速获得大量站点提取能力
3. PotPlayer 外部播放列表通道：VPS 输出只读 .m3u8 专辑
4. 标准播放对象 + 外部播放器路由：PotPlayer / VLC / mpv 的 URL / 文件交付
5. qBittorrent 执行器实验：顺序下载与缓存治理
6. ffmpeg 加工任务：faststart / remux；HLS segment / relay 暂列研究线
7. hls.js / Web 播放：保留为预览能力，不作为主播放承诺
```

这组能力组合起来，形成的是一个可落地的 PureSource 技术底座，而不是单一播放器补丁。

### 2.7 可行性判断与 MVP 收缩路线

当前方案的总体可行性判断是：**方向成立，可行性明确，但必须以最小闭环推进，而不是先做万能播放器。**

这个系统的复杂度来自它本质上不是一个单点播放器，而是一个媒体资源组合系统。可行的原因在于，各个关键环节都有成熟能力可借鉴或接入：

- 浏览器侧运行时嗅探已有 `解析器.md` 作为基础。
- 站点提取和通用 fallback 可借鉴 / 接入 yt-dlp。
- HLS 标准化有 hls.js、hls_m3u8、ffmpeg 等成熟工具链，但 hls.js 在当前阶段只承担预览或特殊场景能力。
- BT 缓存可借助 qBittorrent 的顺序下载、文件选择和 Web API。
- 本地文件和 URL 播放可交给 PotPlayer / VLC / mpv；BT-Player local-stream 负责交付可消费 URL，ffmpeg 负责必要加工。

但不可行的推进方式是：试图一开始解决所有资源、所有站点、所有播放模式，或者让 BT-Player 自己承担源发现、反盗链、BT 即时播放、转码和缓存治理的全部职责。

#### 高可行性：优先推进

- `解析器.md` 改造成 PureSource Browser Agent。
- `yt-dlp --dump-json` 作为外部 fallback。
- PotPlayer 可订阅的只读 `.m3u8` 播放列表。
- m3u8 / HLS 标准播放对象。
- 已完整缓存文件的外部播放器交付。
- qBittorrent 缓存优先实验。
- 缓存状态分级与前端提示。

#### 中等可行性：逐步推进

- ffmpeg remux / faststart。
- 多源关联：magnet + torrent 下载站 + 网页入口归并。
- AI 正片识别、标题编目、跨语言匹配。
- 播放可持续性评分：下载速度、媒体码率、缓冲秒数。
- HLS segment / ffmpeg relay / Web 预览增强。

#### 高难度：暂不承诺

- 极端站点短时 Token 的服务端转发。
- 自定义加扰破解。
- Widevine / DRM。
- 真正无缝的 BT 即时 seek 播放。
- 全自动跨站反爬突破。
- 自研稳定 Web 播放器内核。

#### MVP 建议

后续第一阶段不应追求"所有来源都秒播"，而应先跑通一个稳定闭环：

```text
用户输入 magnet / URL
  → PureSource 识别类型
  → 如果是 HLS / 直链：生成标准播放对象和外部播放器入口
  → 如果是 magnet：提取文件树，识别正片
  → 交给 qBittorrent 缓存
  → 达到 stable 阈值后登记为本地媒体资产
  → BT-Player local-stream 生成可消费 URL / 文件路径
  → 写入 PotPlayer 可订阅 .m3u8 只读播放列表
  → PotPlayer 专辑中直接选择播放
```

这个 MVP 不承诺所有磁链即时播放，也不承诺浏览器 `<video>` 能承担主播放体验。它承诺的是：把一个杂乱资源转化为可理解、可缓存、可检测、可路由的本地媒体资产，并把它交给成熟播放器。只要这条链路跑通，PureSource + BT-Player 的架构就站住了。

## 四、关键设计决策

### 4.1 PureSource 独立于 BT-Player

最初的 BT-Player 承担源发现和播放双重职责。拆分为 PureSource + BT-Player 后，两个服务各自有独立存在价值，通过数据契约通信，可独立演进。

### 4.2 浏览器代理层（解析器.md）是架构的第三极

纯服务端方案无法突破 JS 动态加载、Cloudflare、短时效 Token 等防线。浏览器代理在浏览器运行时执行，天然携带用户登录态，是处理极限场景的必要组件。

### 4.3 提取器注册表模式取代硬编码解析链

借鉴 yt-dlp/lux 的注册表模式，PureSource 内部以 `SourceExtractor` trait 统一提取器接口，支持按需注册新站点提取器。

### 4.4 AI 按任务分流

Hermes Agent（M2.7）处理 95% 日常任务（文件筛选、元数据提取、正片推荐），Gemini 兜底复杂推理（反盗链网页、合集识别）。PureSource 只认一个端点，路由逻辑由 Hermes 内部管理。

### 4.5 推荐引擎是"提纯"的自然延伸

PureSource 不只做"删减"（过滤广告/样本），还要做"推荐"（链路择优、终端适配、场景匹配）。推荐结果嵌入数据契约，随提纯结果一起交付。

### 4.6 播放器端不作为当前主战场

浏览器 `<video>`、自研播放器、HLS/fMP4 全面改造、ffmpeg relay 等方向不是删除，而是降级为后续研究线。当前主战场是资源提纯、缓存治理、质量判断和外部播放器路由。这样可以避免把有限精力投入到播放器端兼容性黑洞里。

### 4.7 磁链本身就是 Web3

项目已半只脚踏在去中心化存储中。IPFS/Arweave 可作为"图书馆存储层"的远期方案，但不进入当前播放主链路。

## 五、架构应对的能力层次

```
  Tier 1: PureSource 完全处理
    场景：磁链（热门种子）、m3u8 直链、普通网页
    特点：完成源提纯、质量判断、缓存策略和外部播放器路由，无需浏览器介入
    占比：~80%

  Tier 2: PureSource + 浏览器代理协作
    场景：反盗链网页、AES-128 加密流、中等地雷站点
    特点：浏览器代理捕获 URL/密钥，PureSource 完成提纯解密，再生成可路由对象
    占比：~15%

  Tier 3: 浏览器内预览 / 特殊场景播放
    场景：短时效 Token、自定义加扰、极端反爬站点
    特点：回到 解析器.md 原有模式，不经过 BT-Player 转发；仅作为兜底，不代表主播放路线
    占比：~4%

  Tier 4: 元数据优先（仅展示，不可播）
    场景：冷门种子 DHT 无 peer、下载站也无法获取
    特点：至少用户知道"里面有什么文件"
    占比：~1%
```

## 八、一句话总结

> **浏览器代理做运行时嗅探，PureSource 做服务端提纯，BT-Player 做缓存治理和播放路由，VPS 输出 PotPlayer 可订阅的只读播放列表，PotPlayer / VLC / mpv 等成熟播放器做最终稳定播放——各层以数据契约耦合，以 Hermes Agent 注入 AI 能力。此前关于 Web 播放、HLS 化和 ffmpeg 中继的设想保留为研究线，但不再作为当前 MVP 的主承诺。**
