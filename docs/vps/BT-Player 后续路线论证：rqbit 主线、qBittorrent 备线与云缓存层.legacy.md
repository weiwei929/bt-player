# BT-Player 后续路线论证：rqbit 主线、qBittorrent 备线与云缓存层

> 日期：2026-05-08  
> 文档性质：Phase 1 前置路线论证，暂不作为实施指令  
> 当前状态：仅用于评估、定调与后续决策；正式推进时间另行决定

---

## 1. 当前边界与事实源

BT-Player 当前已完成 VPS Phase 0 基线加固：服务可运行，API 与 Stream 公网入口已受控，Caddy、systemd、cache_guard 与验收记录已沉淀。

本阶段讨论不再以本地旧 Tauri 项目作为当前事实源。旧项目只保留为创意缘起和历史原型参考；当前事实源优先级为：

1. VPS 实际运行状态；
2. `BT-Player VPS Phase 0 验收记录.md`；
3. 本文档及后续路线评估补充。

本文档只讨论后续路线，不进入 HLS/fMP4、PikPak 实时播放、WebRTC、Jellyfin/Plex、Debrid 等实现。

---

## 2. 总体定位

BT-Player VPS 不应被设计成新的大一统媒体平台，而应先成为一个稳定的 **BT/magnet 即时播放前哨**。

整体媒体体系可按角色划分：

| 模块 | 定位 | 当前策略 |
|------|------|----------|
| `webproxy-ai` | 网页 / 站点 / RSS / 页面资源发现前哨 | 纳入入口层，但不并入 BT-Player |
| `BT-Player VPS` | magnet / torrent 即时探测与边下边播前哨 | 当前主线 |
| `rqbit / librqbit` | BT 流式播放核心能力 | 主线技术基座 |
| `qBittorrent-nox + Web API` | 成熟 seedbox / 稳定下载备线 | 备线与对照组 |
| `PikPak` | 云端离线、温层资产池、冷门资源兜底 | 人工或半自动旁路优先 |
| `Dropbox` | 精选完成品归档 | 不进入 BT 热链路 |

核心链路目标：

```text
发现入口 -> 快速判断 -> 即时播放 / 转存 -> 资产入库 -> 稳定播放 / 长期归档
```

---

## 3. rqbit / librqbit 主线评估

### 3.1 定位

rqbit / librqbit 最贴近当前 BT-Player VPS 的核心目标：对 magnet 或 torrent 进行解析、连接 peers，并通过 HTTP stream 向浏览器提供可播放数据。

它适合承担：

- 即时 magnet 解析；
- peer / DHT / tracker 探测；
- 边下边播；
- 临时缓存；
- 状态反馈；
- 后续 fMP4/HLS 输出层的上游数据源。

### 3.2 优势

1. **目标贴合**  
   rqbit 本身就接近“torrent -> HTTP stream”的模型，比通用下载器更适合即时播放。

2. **体验路径短**  
   用户输入 magnet 后，可以直接进入解析、选文件、播放，不必先完整下载。

3. **便于做阶段状态**  
   可围绕 `resolving / connecting / buffering / playing` 建立状态机和 UI 提示。

4. **适合作为实验沙盘**  
   后续 Remux、缓存策略、冷门资源判断、转存 PikPak 等逻辑都可围绕它扩展。

### 3.3 风险

1. **上游活跃变动带来的可维护性风险**  
   当前已出现过 librqbit 编译兼容问题，说明深度嵌入库会承担上游 API 变化成本。

2. **依赖补丁治理需要持续维护**  
   Phase 0 已通过 vendor 与 local patch 固化依赖，但这只是当前可复现快照，不是长期治理终局。

3. **任务管理能力不如成熟下载器**  
   若未来需要复杂队列、做种、限速、分类、长期下载，rqbit 可能不是最省心方案。

### 3.4 当前结论

rqbit / librqbit 继续作为近期主线，但应保持克制：

- 先巩固“即时探测 + 临时播放 + 状态可见”；
- 不急于把它扩展成完整下载管理器；
- 保留 qBittorrent-nox 作为备线；
- 继续维护依赖补丁快照，避免回到手改 cargo cache。

## 4. qBittorrent-nox + Web API 备线评估

### 4.1 定位

qBittorrent-nox 是成熟 seedbox 路线，更适合长期下载、队列管理、做种、限速、分类和 Web API 自动化。

它不应替代当前 rqbit 即时播放主线，但可以作为：

- 稳定下载备线；
- 冷门或大体积资源的长期下载器；
- rqbit 维护成本过高时的替代底座；
- 与 PikPak 云端离线之间的本地/VPS 下载对照组。

### 4.2 优势

1. **成熟稳定**  
   qBittorrent-nox 是 VPS / seedbox 场景的成熟工具，运维资料多，出问题容易查。

2. **Web API 完整**  
   适合用脚本或后端服务调度添加任务、查询进度、设置文件优先级。

3. **任务管理强**  
   对多任务、长期做种、分类、速度限制、tracker 管理更友好。

4. **作为降级路线可靠**  
   当 rqbit 对某些资源解析、下载、流式播放不稳定时，可转 qBittorrent 完整下载。

### 4.3 风险

1. **不是天然流式播放系统**  
   qBittorrent 的核心是下载管理，不是浏览器即点即播。顺序下载只能辅助播放，不等于完整流媒体服务。

2. **体验链路更长**  
   需要额外解决文件选择、下载进度、HTTP 暴露、播放端访问等问题。

3. **可能诱导系统变重**  
   一旦引入 qBittorrent，容易滑向完整 seedbox / 媒体库系统，与当前“前哨”定位冲突。

### 4.4 当前结论

qBittorrent-nox 暂不进入主线实施，但应作为备线保留：

- 不与 Phase 0/Phase 1 主线耦合；
- 可单独做小规模评估；
- 评估重点不是播放体验，而是稳定下载、任务管理、API 调度和维护成本。

## 5. PikPak 云缓存层评估

### 5.1 定位

PikPak 对当前媒体体系不是普通网盘，而是已有大量资产沉淀的温层仓库。用户已有会员与约 5T 视频资源积累，因此 PikPak 应被视为战略资源，而不是 Debrid 的简单替代品。

PikPak 适合承担：

- 云端离线下载；
- 冷门资源兜底；
- 值得长期保留资源的入库；
- 大体积资源的 VPS 磁盘卸载；
- 已入库资源的后续播放与分发。

### 5.2 优势

1. **已有资产池**  
   5T 级资源积累使 PikPak 成为现成温层，而不是从零开始的外部依赖。

2. **适合冷门资源**  
   当 VPS 直接 BT 下载慢、peer 少、缓存成本高时，可转由 PikPak 离线。

3. **降低 VPS 压力**  
   大文件不必长期占用 Oracle VPS 的 45GB 磁盘。

4. **可与现有项目衔接**  
   `cf-pikpak`、`pikpak-hub`、rclone/WebDAV、HLS 预切片等已有探索可作为后续资产播放层。

### 5.3 风险

1. **不宜成为实时播放硬依赖**  
   若当前主链路直接依赖 PikPak API 或非官方机制，稳定性与维护风险会升高。

2. **API 与账号状态不可完全自控**  
   会员、Token、WebDAV、客户端策略都可能变化。

3. **容易把 BT-Player 变成另一个 PikPak 播放器**  
   这会重复已有项目方向，削弱 BT-Player 作为即时前哨的价值。

### 5.4 当前结论

PikPak 近期只作为 **人工或半自动旁路**：

- 不接入实时播放主链路；
- 保留 cloud export 任务接口作为占位；
- 先记录任务状态、资源 ID、来源类型；
- 后续成熟后再做“转存到 PikPak”或“导出任务”能力。

## 6. Dropbox 归档层评估

### 6.1 定位

Dropbox 不适合进入 BT 热链路，也不适合承担即时播放或离线下载角色。它更适合作为精选完成品归档层。

适合放入 Dropbox 的内容：

- 已筛选、命名稳定、质量稳定的视频；
- 需要跨设备同步的精选内容；
- 长期保留的创作素材或成品；
- 不需要频繁变动的媒体资产。

### 6.2 当前结论

Dropbox 只做归档，不参与：

- magnet 解析；
- BT 下载；
- 即时播放；
- 冷门资源探测；
- 临时缓存。

---

## 7. 明确不做

近期不做以下路线：

1. **Jellyfin / Plex**  
   当前不需要完整媒体库服务器，不引入。

2. **Debrid / 缓存云服务**  
   不作为主线。PikPak 已承担部分云缓存价值，且用户希望保持更强自主性。

3. **WebRTC / 混合网关**  
   作为长期观察项，不进入近期实施。

4. **PikPak 实时播放硬耦合**  
   只保留旁路与导出占位，不把它作为当前播放主链路依赖。

5. **大一统媒体平台**  
   当前只推进前哨与路由判断，不重启“大平台”建设。

## 8. 路由决策表

| 场景 | 推荐路线 | 原因 |
|------|----------|------|
| 想马上判断 magnet 是否可看 | rqbit / BT-Player VPS | 最短路径，即时探测 |
| peer 尚可、只是临时观看 | rqbit / BT-Player VPS | 不必入库，不占长期空间 |
| rqbit 解析慢、peer 少、资源冷 | PikPak 旁路 | 云端离线更适合冷门资源 |
| 资源明确值得长期保留 | PikPak | 进入温层资产池 |
| 需要完整下载、长期做种或复杂任务管理 | qBittorrent-nox | 成熟 seedbox 能力 |
| 已整理完成、质量稳定、长期收藏 | Dropbox | 精选归档 |
| 网页 / 视频站 / RSS / 论坛入口 | webproxy-ai | 页面级资源发现前哨 |
| 已有 m3u8 / mp4 直链 | webproxy-ai 或播放器层 | 不必进入 BT 链路 |

## 9. Phase 1 推荐实施顺序

本文档不要求立即实施。若未来正式推进，建议顺序如下：

1. **路线冻结**  
   固定本文档中的角色分工和不做事项。

2. **入口契约定义**  
   定义统一资源提纯结果，例如：

   ```json
   {
     "kind": "magnet | torrent | hls | mp4 | pikpak_share | article | list",
     "sourceUrl": "...",
     "title": "...",
     "confidence": 0.82,
     "nextAction": "play_now | probe_bt | save_to_pikpak | collect | reject",
     "reason": "..."
   }
   ```

3. **BT-Player VPS 状态反馈增强**  
   优先做 `resolving / connecting / buffering / playing / swarm_cold` 状态可见。

4. **PikPak 导出任务半自动化**  
   在不接实时播放的前提下，让 cloud export 占位任务能承接人工转存流程。

5. **qBittorrent-nox 小规模备线验证**  
   单独验证 API、任务添加、顺序下载、文件优先级、下载完成后暴露路径。

6. **再评估 HLS/fMP4 输出层**  
   等主线前哨稳定后，再决定是否做播放输出升级。

## 10. 风险与观察指标

| 风险 | 观察指标 | 应对 |
|------|----------|------|
| rqbit 上游变动 | 构建失败、补丁增多 | 维持 vendor + local patch，必要时转 qBittorrent 备线 |
| VPS 磁盘压力 | cache_guard 触发频率、缓存占用 | 应用级缓存淘汰 |
| 冷门资源体验差 | 0 peer 时长、首播等待时间 | 转 PikPak 旁路 |
| PikPak 依赖过深 | API 失败率、Token 刷新问题 | 保持人工/半自动，不做实时硬依赖 |
| 项目重新发散 | 新方向数量、未完成链路数量 | 新方向先入观察池 |

---

## 11. 当前结论

近期主线保持：

```text
rqbit / BT-Player VPS = 即时播放前哨
qBittorrent-nox = 稳定下载备线
PikPak = 云缓存与温层资产池
Dropbox = 精选归档
webproxy-ai = 网页资源发现前哨
```

当前不急于推进实现。下一步若启动 Phase 1，应先围绕“入口契约 + 状态反馈 + PikPak 半自动旁路”做小闭环，而不是重启大一统媒体平台。
