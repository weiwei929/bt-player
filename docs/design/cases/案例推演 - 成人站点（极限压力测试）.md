# 案例推演：成人站点——架构极限压力测试

> 目的：用最严苛的源类型验证 PureSource 架构的天花板
> 原则：如果这类站点能搞定，市面上就没有 PureSource 处理不了的源

---

## 为什么这类站点是"终极考验"

| 防线 | 普通视频站 | 成人站 | 突破手段 |
|------|-----------|--------|---------|
| Cloudflare | 可选 | **几乎必开**，且为最严等级（5秒盾 + 挑战页面） | curl-impersonate + 浏览器代理 |
| JS 混淆 | 轻度 | **重度混淆**，eval + 动态生成 + 反调试 | 必须浏览器运行时，服务端不可能 |
| 视频加密 | AES-128 常见 | **AES-128 + 自定义加扰**，密钥动态获取 | hook 浏览器中密钥获取点 |
| Referer/Origin | 单层 | **多层链式校验**：Referer → Token → 时间戳签名 | 浏览器代理从页面实时提取 |
| 鉴权 | 无需/简单 | **Cookie + 登录态 + 短时效 Token** | 浏览器代理共享用户登录态 |
| IP 封锁 | 宽松 | **严格**，单 IP 请求频率极低 | 随用户浏览器请求，不直接 VPS 请求 |
| CDN 策略 | 标准 | **限制 IP 地区 + ISP** | 浏览器代理天然满足 |
| 法律风险 | 低 | 高 | 用户在自己浏览器触发，非服务端主动爬取 |

## 场景设定

用户在浏览某成人站（以 91porn 为原型，但适用于所有同类站点），看到一部想看的视频。

用户的操作路径：

```
用户已登录该站点
  │
  ├── 页面由 Cloudflare 保护
  ├── 视频播放器是自定义 JS 控件
  ├── 视频源经过多层混淆和鉴权
  └── 浏览器代理（解析器.md 改编版）已启用
```

## 管线全程追踪

### ① 页面加载

```
用户打开视频播放页
  │
  ├── Cloudflare 验证（5秒盾）
  │     └── 浏览器自动通过，用户无感
  │
  ├── 页面加载
  │     └── Cloudflare 已下发清除了挑战的页面
  │
  └── 浏览器代理（油猴脚本）启动
        └── 注意：油猴脚本在 Cloudflare 验证之后才执行
        └── 因此脚本不受 Cloudflare 影响
```

### ② 浏览器代理捕获

```
视频播放器 JS 开始执行：

  第 1 层：播放器初始化
    └── JS 通过 eval + 动态拼接构建播放器
    └── 浏览器代理无法直接解析静态 HTML

  第 2 层：Token 握手
    └── XHR POST /api/video/token → 返回加密 token
    └── XMLHttpRequest 钩子捕获响应
    └── 但 payload 是加密的，对规则引擎不可读

  第 3 层：获取 m3u8
    └── fetch(`/api/video/play?token=${encryptedToken}`)
    └── Response.prototype.text 钩子捕获响应
    └── 响应体是 #EXTM3U 开头 → 命中 m3u8 检测 🎯
    └── URL: https://cdn91.com/hls/abc123/master.m3u8?sign=xxx&exp=yyy

  第 4 层：密钥获取
    └── m3u8 manifest 包含 #EXT-X-KEY:METHOD=AES-128,URI="/api/video/key"
    └── 浏览器代理的 XHR 钩子捕获到 key 请求
    └── 但 key 请求需要 Cookie + Referer + 自定义 Header
    └── 浏览器代理天然携带这些，请求成功 → 捕获密钥 🎯
```

### ③ 浏览器代理 → PureSource 提交

````json
{
  "source": "browser-agent",
  "tabUrl": "https://www.example91.com/view.php?id=12345",
  "detectedUrls": [
    {
      "url": "https://cdn91.com/hls/abc123/master.m3u8?sign=xxx&exp=yyy",
      "detectMethod": "response_hook",
      "mimeType": "application/vnd.apple.mpegurl",
      "manifestInfo": {
        "playlists": [
          {"uri": "1080p.m3u8", "resolution": "1920x1080", "bandwidth": 5000000},
          {"uri": "720p.m3u8",  "resolution": "1280x720",  "bandwidth": 3000000},
          {"uri": "480p.m3u8",  "resolution": "854x480",   "bandwidth": 1500000}
        ],
        "encrypted": true,
        "keyUri": "/api/video/key"
      },
      "pageContext": {
        "cookies": ["PHPSESSID=abc...", "user_token=xyz..."],
        "referer": "https://www.example91.com/view.php?id=12345",
        "customHeaders": {"X-Requested-With": "XMLHttpRequest"}
      }
    }
  ]
}
````

### ④ PureSource 的处理局限

```
PureSource 收到浏览器代理提交的 URL
  │
  ├── hls_m3u8 crate 解析 manifest → ✅ 成功
  │     └── 找到 3 个码率
  │
  ├── 加密检测 → #EXT-X-KEY 存在
  │     ├── PureSource 尝试从密钥 URL 获取密钥
  │     │     └── GET /api/video/key
  │     │           └── 403 ❌ — 缺少 Cookie + 自定义 Header
  │     │
  │     └── 结论：PureSource 服务端无法解密
  │           └── 需要浏览器代理协助密钥获取
  │
  ├── 防盗链检测
  │     └── Referer 已知 → ✅
  │     └── sign + exp 参数 → 短时效，PureSource 拿到后可能已过期
  │
  └── 结论：PureSource 核心能力在这里大幅受限
```

### ⑤ 架构调整：浏览器代理不再是"传递者"，而是"执行者"

对于这类极限站点，**PureSource 的服务端处理能力大幅下降**，需要**浏览器代理承担更多执行职责**：

```
原来（普通站点）：
  浏览器代理 → 捕获 URL → 传给 PureSource → PureSource 做一切

现在（极限站点）：
  浏览器代理 → 捕获 URL、密钥、Cookie → PureSource 尝试服务端处理
                ↓ 如果失败
              浏览器代理代理下载 TS 分片并转发
```

浏览器代理的**降级执行方案**：

```
┌─ 浏览器（用户已登录）─────────────────────────────────────┐
│                                                            │
│  浏览器代理                                                │
│    ├── 捕获 m3u8 URL  →  传给 PureSource                   │
│    ├── 捕获 AES 密钥  →  传给 PureSource                   │
│    ├── 捕获 Cookie    →  传给 PureSource                   │
│    │                                                       │
│    └── 如果 PureSource 仍无法解码（例如 Token 时效极短）     │
│          ├── 浏览器代理启动"代理下载"模式                    │
│          │    └── 在浏览器中 fetch TS 分片（天然满足鉴权）    │
│          │    └── 通过 Service Worker 或 Blob URL 拼接      │
│          │    └── 输出可播放的视频                           │
│          │                                                 │
│          └── 或：直接把视频在浏览器中播放（回到 解析器.md 原有模式）│
│                                                                │
└────────────────────────────────────────────────────────────┘
```

### ⑥ BT-Player 播放

```
场景 A：PureSource 成功获取密钥
  └── PureSource 解密 m3u8 + TS 分片
  └── 输出解密后的标准 HLS 流
  └── BT-Player <video> 直接播放 ✅

场景 B：PureSource 无法获取密钥（最常见）
  └── PureSource 返回未解密的流 + 标记 "requires_browser_proxy"
  └── BT-Player 返回浏览器代理直连模式
  └── 浏览器中直接用原页面的 Cookie 播放
  └── 播放体验：略低于 PureSource 直出，但可用

场景 C：Token 时效极短（分钟级）
  └── 走场景 B，或浏览器代理在浏览器内直接播放
  └── 不经过 BT-Player 转发
```

## 管线三：hsex.tv 列表页——批量发现场景

### ① 场景特征

不同于前两条管线用户已经有了具体目标，这次用户是在 **浏览**：

```
用户打开 https://hsex.tv/list-1.htm
  │
  ├── 这是一个分类列表页，不是单个视频页
  ├── 每页 20-30 个视频缩略图
  ├── 分页：list-1.htm, list-2.htm, ...
  └── 用户想"看看有什么好看的"
```

这带来一个全新的挑战：**PureSource 之前所有的设计都是"单输入→单输出"，但列表页是"单输入→多输出"**。

### ② 浏览器代理：批量扫描模式

```
浏览器代理检测到页面类型：

  第 1 步：页面类型识别
    └── 页面包含多个 <a> 指向 /view/xxx.html
    └── 页面结构符合列表页模式（缩略图网格 + 分页）
    └── 浏览器代理自动切换到"列表扫描模式"

  第 2 步：提取所有视频链接
    └── 扫描页面上所有链接
    └── 过滤出匹配 /view/xxx.html 模式的 URL
    └── 提取每个条目的：标题 / 缩略图 / 时长 / 预览图
    └── 本次扫描发现 24 个视频条目

  第 3 步：提交给 PureSource（不深入单个页面）
    └── POST /purify/batch
    └── 提交的是列表页上下文，不是逐个视频页
```

### ③ 浏览器代理 → PureSource 提交

```json
{
```

### ④ PureSource 的处理

```
PureSource 收到列表扫描结果
  │
  ├── 与之前的"单视频提纯"完全不同
  │     └── 没有实际的视频 URL 需要提纯
  │     └── 而是收到了 24 个"候选视频"的元数据
  │
  ├── PureSource 的角色转变：
  │     提纯者 → 索引者
  │     即时处理 → 按需预取
  │
  ├── 策略 A：懒加载（推荐）
  │     └── 只编目这 24 条元数据（标题+时长+缩略图）
  │     └── 存入临时索引，给用户展示
  │     └── 用户点击某个视频时，才启动单视频提纯管线
  │     └── 优点：不浪费资源，hsex.tv 有 342 页 × 24 条 = 8208 个视频
  │
  ├── 策略 B：预取热门（可选增强）
  │     └── 对当前页的 24 个视频，选择前 3-5 个
  │     └── 自动打开新标签页进行浏览器代理捕获
  │     └── 用户浏览列表时，后台已准备好部分视频源
  │
  └── 对列表页的后续翻页
        └── 浏览器代理在用户滚动到页底时自动识别翻页链接
        └── 用户进入第 2 页 → 浏览器代理再次扫描 → 提交 PureSource
        └── PureSource 关联会话：同一用户的多次扫描归入一个"浏览会话"
```

### ⑥ 新挑战：列表页的规模效应

```
hsex.tv 有 342 页列表，每页 24 条，总计 8208+ 个视频。

如果用户深度浏览（翻很多页），浏览器代理和 PureSource 之间
的通信量会急剧增加：

  单页扫描：~3KB JSON（24 条）
  全部扫描：~1MB JSON（8208 条）
  如果每条都打开页面提取视频源 → 不可能

解决方案：纯元数据浏览 vs 按需提纯
  └── 列表页阶段：只传元数据（标题、时长、缩略图 URL）
  └── 用户点击阶段：才打开具体视频页做完整提纯
  └── 用户的浏览会话状态由 PureSource 管理（轻量级，内存即可）
```

## 管线四：论坛多链路组合——磁链 + 种子文件 + 下载站

### ① 输入

用户在论坛看到一个帖子，提供了三种方式下载同一资源：

```
【种子名称】: XHYRQSF5.1.torrent
【磁力连接】: magnet:?xt=urn:btih:E4452B47A0DEF4AE7E271FB3DBBA5C92594C1DBB
【下载网址】: https://dww.downoc.cc/link.aspx?hash=E4452B47A0DEF4AE7E271FB3DBBA5C92594C1DBB
```

用户的操作方式：

```
用户选中三行文本，一键粘贴到 BT-Player 输入框
  │
  ├── 输入包含三种不同类型的链接
  ├── 但它们指向同一资源（同一 infohash）
  └── 用户期望：BT-Player 自动识别 → 选最优方式播放
```

### ② PureSource 输入解析

```
PureSource 收到多行输入
  │
  ├── 文本分割 → 识别出 3 个独立条目
  │     ├── ① XHYRQSF5.1.torrent → 种子文件名（非链接）
  │     ├── ② magnet:?xt=urn:btih:E4452B47... → 磁链
  │     └── ③ https://dww.downoc.cc/link.aspx?hash=... → 下载站 URL
  │
  ├── 关联分析
  │     └── 所有条目的 hash 一致（E4452B47A0DEF4AE7E271FB3DBBA5C92594C1DBB）
  │     └── XHYRQSF5.1 正是这个 infohash 的前 10 位 Base32 编码
  │     └── 结论：三者指向同一资源 ✅
  │
  └── 输出：关联资源组（ResourceGroup），内部包含 3 个候选源
```

### ③ 逐源评估

```
┌────────────────────────────────────────────────────────────────┐
│  资源组：E4452B47A0DEF4AE7E271FB3DBBA5C92594C1DBB              │
│  标题：XHYRQSF5.1（编码名，AI 可尝试解码或忽略）                   │
├────────────────────────────────────────────────────────────────┤
│                                                                │
│  候选源 A：磁链（最高优先级）                                    │
│  └── magnet:?xt=urn:btih:E4452B47...                          │
│  └── 评估：可直达，通过 librqbit 解析+下载                        │
│  └── 风险：种子冷门程度未知，可能无做种者                          │
│  └── 动作：立即尝试连接 DHT 网络                                  │
│                                                                │
│  候选源 B：下载站（备选）                                        │
│  └── https://dww.downoc.cc/link.aspx?hash=E445...              │
│  └── 评估：提供 .torrent 文件直链，可绕过 DHT 直接获取种子元数据    │
│  └── 风险：下载站可能有 Referer 防盗链、频率限制、验证码            │
│  └── 动作：尝试 HTTP GET 获取 .torrent 文件                      │
│                                                                │
│  候选源 C：种子文件名（辅助信息）                                 │
│  └── XHYRQSF5.1.torrent                                        │
│  └── 非链接，但提供了种子文件名线索                               │
│  └── 价值：AI 可尝试解码文件名（可能是 Base32 编码的时间戳+ID）     │
│                                                                │
└────────────────────────────────────────────────────────────────┘
```

### ④ 下载站的实际挑战

```
PureSource 尝试获取候选源 B → HTTP GET link.aspx

  第 1 次尝试：无 Referer
    └── HTTP 302 重定向到验证页
    └── https://dww.downoc.cc/verify.aspx?return=...
    └── ❌ 防盗链触发

  第 2 次尝试：附加论坛 URL 作为 Referer
    └── HTTP 200，但返回的是 HTML 等待页
    └── "请等待 30 秒后开始下载..."
    └── 页面包含 JS 倒计时 + 可能是 Cookie 验证
    └── ❌ 需要浏览器运行时

  第 3 次尝试：交给浏览器代理处理
    └── 用户在论坛帖子页面时，浏览器代理已捕获该链接
    └── 浏览器代理的 XHR 钩子捕获到最终的 .torrent 文件下载
    └── 浏览器代理将 .torrent 文件内容 Base64 传给 PureSource
    └── ✅ 成功获取
```

**这里的关键洞察**：下载站是整个链条中最薄弱、也是最有价值的环节。因为：

```
如果 DHT 网络无做种者（冷门种子的常见情况）：
  ├── 磁链 → 卡死在"connecting to peers"，永远下不了
  │
  ├── 下载站 → 只要绕过防盗链，就一定能拿到 .torrent 文件
  │     └── .torrent 包含元数据（文件名、文件列表、分片哈希）
  │     └── 有了元数据，PureSource 可以做文件筛选 + AI 编目
  │     └── 即使下不动，至少知道里面有什么
  │
  └── 下载站的价值：在 DHT 失效时提供"元数据逃生通道"
```

### ⑤ 多链路关联的核心逻辑

```
用户粘贴多行文本
  │
  ├── 文本解析器（新增 PureSource 组件）
  │     └── 正则分割：按行 / 按【关键词】: / 按 URL 格式
  │     └── 提取出 3 类条目：链接 / 磁链 / 种子文件名
  │     └── 对每条做类型识别和标准化
  │
  ├── 关联引擎（新增 PureSource 组件）
  │     └── 从多个条目中计算 infohash
  │         ├── 磁链 → 直接提取
  │         ├── 下载站 URL → 从 hash 参数提取
  │         └── 文件名 → 尝试 Base32 解码
  │     └── 如果 hash 一致 → 合并为同一资源组
  │     └── 如果 hash 不同 → 分别独立处理
  │
  └── 输出：资源组（ResourceGroup）
        └── 内部包含多个候选源（CandidateSource）
        └── 每个候选源有独立的可用性状态
```

## 架构冲击：PureSource 的"能力天花板"

```
普通站点                         极限站点
─────────                      ────────
PureSource 负责全流程           PureSource 只能做一部分
  源发现 → 服务端                 源发现 → 浏览器代理
  提纯 → 服务端                   提纯 → 部分服务端 + 部分浏览器代理
  编目 → 服务端                   编目 → 服务端（信息足够时）
  入库 → 服务端                   入库 → 服务端

                                浏览器代理新增职责：
                                  协助密钥获取
                                  代理 TS 分片下载
                                  携带实时登录态
```

### 核心结论

| 能力 | 是否突破 | 来源管线 | 说明 |
|------|---------|---------|------|
| Cloudflare | ✅ 突破 | 单视频 | 油猴脚本在 Cloudflare 验证之后执行，天然绕过 |
| JS 混淆 | ✅ 突破 | 单视频 | 不解析 JS，直接 hook 网络请求，混淆不影响 |
| Referer/Origin | ✅ 突破 | 单视频 | 浏览器代理从页面上下文提取，实时准确 |
| Cookie/登录态 | ✅ 突破 | 单视频 | 用户已登录，浏览器代理共享登录态 |
| AES-128 加密 | 🟡 有条件 | 单视频 | 密钥在浏览器中可捕获，但需浏览器代理协助传递 |
| **短时效 Token** | **🔴 最难** | 单视频 | Token 分钟级过期，传给 PureSource 已无意义。最终只能**浏览器内直接播放** |
| **自定义加扰** | **🔴 取决于实现** | 单视频 | JS 层加扰可插桩，Native 层加扰无法突破 |
| IP 地区限制 | ✅ 突破 | 单视频 | 请求来自用户浏览器，非 VPS |
| **列表页批量扫描** | **🟡 新模式** | hsex.tv | 从"单输入→单输出"变为"单输入→多输出"，PureSource 角色从**提纯者**转变为**索引者** |
| **分页翻页追踪** | **🟡 新模式** | hsex.tv | 342 页列表，不能全扫，必须**按需懒加载**，用户点击后才触发单视频提纯 |
| **多链路关联去重** | **✅ 需新增组件** | 论坛组合 | 磁链/下载站/文件名 → 关联引擎计算 infohash → 归并同一资源组 |
| **下载站防盗链** | **🟡 有条件** | 论坛组合 | 30 秒等待页 + JS 倒计时 + Cookie 验证，需要浏览器代理捕获最终 .torrent |
| **DHT 元数据逃生** | **🟢 新发现** | 论坛组合 | 下载站的价值不仅在于下载，更是**冷门种子元数据的唯一来源**——DHT 无 peer 时唯一知道文件列表的途径 |

## 总结：这句话说得对

> **"如果这类站点都能解决，就意味着项目能力到顶了"**

通过这个案例可以看到：

1. **PureSource 的天花板是服务端无法持有用户登录态**。这是架构层面的限制，不是实现层面的限制。

2. **浏览器代理从"辅助"升级为"核心"**。在极限场景下，浏览器代理不再是 PureSource 的触角，而是**执行主体**。PureSource 退居"编排者"角色。

3. **Tier 3（浏览器内直接播放）是最后的保险**。如果所有转发都失败，解析器.md 原有的"在浏览器中直接捕获→下载→播放"能力就是底牌。这也是你保留解析器.md 独立功能的先见之明。

4. **但绝大多数视频不需要走 Tier 3**。非成人站点的反爬远没有那么严，m3u8、磁链、普通网页这些主流场景 PureSource 服务端完全可以覆盖。极限站点的突破能力是**上限保障**，不是日常路径。

### 四份案例推演的能力覆盖全览

| 维度 | Yanni 演奏会 | 上帝也疯狂 1&2 | 成人站点 | 新增管线（hsex + 论坛） |
|------|-------------|---------------|---------|----------------------|
| **源类型** | magnet + 网页 + m3u8 | magnet + m3u8 | HLS 加密流 | **列表页 + 多链路组合** |
| **核心挑战** | 文件筛选 + 防盗链 | 合集识别 + 冷门种子 | JS 混淆 + 短时效 Token | **批量发现 + 多源关联** |
| **PureSource 角色** | ✅ 全权处理 | ✅ 全权处理 | 🟡 协作 | **🆕 索引者 + 编排者** |
| **浏览器代理角色** | 可选 | 可选 | **必需** | **🆕 列表扫描 + 下载站救援** |
| **推荐引擎重心** | 格式适配 | 源择优 | 播放分级 | **🆕 候选源自动切换** |

### 一句话总结整个压力测试

> PureSource + BT-Player + 浏览器代理 = **三条管线覆盖 95% 场景，Tier 4 兜底剩下 5%。成人站点是上限测试，不是日常路线。日常 80% 的流量走磁链和 m3u8，PureSource 服务端完全可以独立处理。**
